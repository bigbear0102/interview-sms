## 미검증/주의
- **실제 폰 종단 시험 전**: 게이트웨이 API 경로/응답, 웹훅 payload, 앱 QR 연결 방식은 문서 기준.
- 법정 보관기간 기본값은 법무 확인 필요.
- 무료 플랜 처리량 ≈ 25건/분. 대량(수천 건) 발송이 잦으면 유료 플랜 + `SEND_BATCH` 상향.
- 현재 Cloudflare 계정은 로그인된 wrangler 계정(`workers.dev` 서브도메인 `bigbears`)이다. 회사 도메인/계정으로 옮길 때는 `wrangler.jsonc`의 D1 id 와 시크릿을 새로 만든다.

## 2026-10-15 웹을 Cloudflare Workers 로 이전
- 도메인(`interview.bigbears.me`)은 DNS 를 바꾸지 않고 Worker route 로 가로챔. 웹훅 주소/토큰이 그대로라 폰 쪽 변경 없음.
- 데이터는 `deploy/cloudflare/export-to-d1.mjs` 로 SQLite → D1 이전, 시크릿은 `put-secrets.mjs`.
- **남은 PC 의존**: 게이트웨이 서버(Docker). 상시 서버(예: Cloudflare 계정에 터널이 있는 Oracle/홈서버, 또는 회사 서버)로 옮기면 PC 는 완전히 불필요.
- Workers 무료 플랜 발송 처리량 ≈ 25건/분(시간당 1,500건). 대량 발송이 잦으면 유료 플랜 + `SEND_BATCH` 상향.
- 회사 서버 이전 시 D1 → SQLite: `deploy/cloudflare/import-d1-export.mjs` (검증 완료).

## 2026-10-15 게이트웨이를 공개 클라우드(api.sms-gate.app)로 전환 + 종단간 암호화
- 사용자 결정: PC/서버 없이 운영. 대신 번호/내용이 제3자 서버를 거치므로 **앱의 passphrase 종단간 암호화**를 필수로 안내한다.
- 암호화 대상: 문자 내용(`textMessage.text`)과 받는 번호(`phoneNumbers`). 형식 `$aes-256-cbc/pbkdf2-sha1$i=<반복>$<salt>$<암호문>` (테스트로 앱 규격 복호화 검증).
- 한계: 폰이 서버로 올리는 **받은 문자(답장) 내용의 암호화 여부는 문서에 명시되지 않음**. 웹훅은 폰 → 우리 Worker 로 직접 가므로 공개 서버를 거치지 않는다.
- 기기 키 기반 E2E(RSA-OAEP, MGF1=SHA-1)는 WebCrypto 가 OAEP 와 MGF1 해시를 분리 지정할 수 없어 Workers 에서 구현 불가 → passphrase 방식 사용.
- 비용/성능: 필드당 PBKDF2 비용이 있어 Workers 무료 플랜(CPU 10ms)에서는 반복 횟수를 낮춰야 한다. 대량 발송은 유료 플랜 권장.

## 2026-10-15 운영 안정성 1단계
- 폰 상태 점검(5분)·장애/복구 메일, 오류 급증 메일, `/healthz` DB 확인, 안전 배포 스크립트(마이그레이션 선행), 백업 스크립트와 Time Travel 복구 절차, GitHub Actions CI.

- 한계: 발송 요청이 서버에 접수(202)된 것만 "보냄"으로 기록한다. 실제 전달 결과(`delivered`)는 2단계에서 반영한다.

## 2026-10-15 운영 안정성 2단계: 전달 결과 · 자동 재시도 · 새 답장 알림
- 발송 응답의 메시지 id(`gw_msg_id`)를 저장하고, 웹훅(`sms:sent|delivered|failed`)과 2분 주기 서버 조회로 전달 상태를 반영한다. 웹훅 등록은 이벤트 4종.
- 재시도: 총 3회(2분, 10분 간격), 영구 오류(400/401/403/404/422)는 즉시 실패. 전달 실패 이벤트도 같은 정책으로 재시도하며, 완료된 캠페인은 다시 `sending` 으로 돌린다.
- 답장을 이미 한 사람의 전달 실패 이벤트는 상태를 바꾸지 않는다(회신이 더 강한 증거).
- 새 답장 메일은 **내용·번호 없이 링크만**, 사용자별 선택(기본 꺼짐), 5분에 1회. 안 읽은 문자는 부서 공유 받은편지함 기준(`inbound.read_at`).
- **한계(운영 시험으로 확인)**: 이 환경에서는 서버 상태가 `Sent` 에서 `Delivered` 로 바뀌지 않았다(통신사 전달 확인 없음). "전달됨"은 전달 확인이 오는 환경에서만 표시된다.

## 메일 수신 지원자 수신함 (2026-10)
- 알바몬 지원 알림 메일에는 이름·공고·이력서 링크만 있고 연락처는 없다(알바몬이 "개인정보 보호를 위해 연락처를 노출하지 않습니다"). 연락처는 이력서 페이지(로그인 필요)에서만 확인된다.
- 서버가 알바몬에 로그인해서 수집하는 방식은 택하지 않았다(계정·약관 위험, 비밀번호 저장). 대신 **담당자가 로그인한 화면**에서 한 번 눌러 전화번호를 읽어 오는 북마크 도구와 수동 입력을 둔다. 도구는 주소의 `#`(조각) 뒤로 정보를 넘겨 서버 로그에 남지 않게 한다.
- 메일은 Cloudflare Email Routing → Worker `email()` 로 받는다. 수신 주소는 `apply-<토큰>@도메인` 하나만 허용(토큰은 DB 설정, 관리자가 재생성). 메일 원문은 저장하지 않는다.
- 연락처 가져오기(2026-10): 알바몬 이력서는 로그인 + "연락처 보기" 클릭이 필요하다. Workers 에서는 브라우저를 돌릴 수 없고 계정을 서버에 둘 이유도 없어서, **담당자 PC의 에이전트(`tools/albamon-agent`)** 가 크롬으로 로그인·클릭·읽기를 하고 결과만 `/api/agent/*`(에이전트 토큰, 해시 저장)로 돌려준다. 알바몬 계정은 서버에 저장하지 않는다. 건별 요청만 처리하고, 차감·결제 확인 창에서는 멈춘다.

## 사람별 확장 프로그램·수신함 담당자 (2026-10)
- 요구: 메일과 그룹웨어는 각자의 계정으로 가져와야 한다. 그룹웨어 아이디·비밀번호는 **서버에 저장하지 않는다**(비밀번호를 서버 DB에 두면 확장 프로그램을 만든 이유가 사라진다). 확장 프로그램(내 PC 크롬)이 `chrome.storage.local`에만 저장하고 그룹웨어 로그인 화면에만 입력한다.
- 연결 키는 사람별(`agent_tokens`, 해시 저장). 예전 공용 키는 담당자 없음(NULL) 키로 계속 동작한다. 수신함 건에는 `owner_user_id`(NULL = 공용). 일반 사용자는 내 건+공용 건, 관리자는 전체.
- 에이전트 API는 키의 주인 기준으로 큐·결과를 제한한다(남의 건 결과는 404). `POST /api/agent/mail`은 확장이 그룹웨어에서 읽은 본문 HTML을 받아 **서버의 검증된 해석기**(`parseAlbamonApply`)로 해석·저장한다(확장에 정규식을 중복 구현하지 않는다). 이력서 링크는 `*.albamon.com`(https)만 저장한다(확장이 그 주소를 열기 때문).
- 메일함 번호(mailboxId)는 사람마다 달라서 목록의 `data-mailbox-id` 속성에서 읽는다. 처리한 메일 번호는 확장이 로컬에 기억해 다시 열지 않는다(5분마다 스캔, 한 번에 15건).
- 알려진 한계: `applicant_inbox`의 `UNIQUE(source, apply_no)` 때문에 같은 지원 번호는 한 사람의 수신함에만 들어간다. 그룹웨어 화면(DOM)이 바뀌면 확장의 목록·본문 찾기를 고쳐야 한다(`mock-ext.mjs`로 확인).

## 공고별 정리·지원 건 칸 정의 (2026-10)
- 문제: 알바몬 메일로 등록된 지원 건의 "지원한 곳"에 알바몬 근무회사명(우리 계정명, 모두 같은 값), "직무"에 공고 제목 전체가 들어가 있었다. 의미가 다른 값을 같은 칸에 넣은 것이 원인.
- 정의: `applicant_applications.applied_to` = **원가중심점**, `job` = **직무**(화면 이름만 바꾸고 칼럼·필터·CSV 로직은 유지). 알바몬 원본은 `recruit_no`·`posting_title`·`company_raw`에 따로 보관한다.
- 0020 마이그레이션이 기존 메일 등록 건을 원본 보존하며 비운다(근무회사명과 같은 값만 비움, 직접 입력한 값은 유지). 비어 있고 공고번호가 있는 건은 "정리 필요".
- 바로잡기는 **공고 단위**(UX: 16명이 공고 1~2개면 입력 2번). 저장하면 그 공고의 지원 건 전체 + 수신함 대기 건에 적용하고 `inbox_cost_rules(recruit_no → 원가중심점·직무)`로 기억해 이후 메일에 자동 적용. 원가중심점 목록이 있으면 목록 안의 이름만 허용. 공고 제목 대괄호 안 이름으로 목록에서 **제안만** 한다(자동 확정 안 함).
- 같은 사람이 같은 공고(공고번호)로 다시 지원하면 지원 건을 중복으로 만들지 않는다.
- 미구현 후보(정보 더 가져오기): 지원 일시(그룹웨어 목록 날짜), 알바몬 계정, 이력서의 이메일·희망 직종·경력 상세, 공고 상세의 근무지·직종(직무 제안용). 생년월일·사진·자기소개는 가져오지 않는다. 새 개인정보 칼럼은 `purgeExpired` 파기 처리 필요.

## 사람별 수신 주소·웹에서 그룹웨어 계정 입력 (2026-10)
- 수신 주소는 사람별(`user_mail_addr`, `apply-<이름>@도메인`, 이름은 본인이 변경). 공용 주소(비밀 토큰)는 관리자용으로 유지. `email()`은 공용 토큰 → 사람별 이름 순으로 확인하고 사람별 주소로 온 메일은 그 사람의 수신함(owner)에 넣는다. 사람별 이름을 모두 받으려면 Email Routing catch-all → Worker 가 필요(알 수 없는 주소는 Worker 가 거절).
- 그룹웨어 비밀번호를 웹에서 입력하되 **서버에는 보내지 않는다**: 화면(`ext-bridge-page.js`)이 양식 전송을 막고 `postMessage`로 확장의 content script(`bridge.js`)에 건네며, 확장은 `chrome.storage.local`에만 저장한다. 화면에는 저장 여부만 돌려준다. 확장은 허용된 출처(시스템 주소)의 화면에서 온 메시지만 받는다. 연결 키도 같은 길로 자동 입력.
- 수신함 "다시 대기로": 무시뿐 아니라 **등록한 건**도 대기로 돌린다(등록된 지원자는 그대로 두고 재등록은 같은 번호·같은 공고를 중복으로 만들지 않는다). 예전에는 등록한 건 버튼이 아무 반응이 없었다.

- 그룹웨어 메일 가져오기 속도(2026-10, 확장 v1.2.2): 메일마다 화면을 열어 기다리던 방식(건당 수 초)을 그룹웨어의 메일 보기 API(/mail/data/emlMail/selectMailView.do, 응답 mailList[0].emlMessageVo.content)를 로그인된 탭에서 직접 호출하는 방식으로 바꿨다(건당 약 0.1초, 4건 동시, 1회 최대 40건; 실제 21건 약 9초). 이 API 구조가 바뀌면 pageFetchBodies를 고쳐야 한다. 받지 못한 건은 기억하지 않아 다음 확인 때 다시 시도한다.
- 실패 이유 표시(2026-10, 확장 v1.2.3): 확장의 상태를 단계(info/ok/warn/error)와 함께 저장하고, 그룹웨어 로그인 실패·목록 못 읽음·본문 못 받음·알바몬 로그인 필요·이용권 창·시스템 연결 실패 등을 **해야 할 일과 함께** 문장으로 남긴다. 수신함 화면은 3초마다 확장 상태를 읽어 "최근 결과"를 색(빨강/노랑/초록)으로 보여 주고, 팝업도 같은 색을 쓴다. 새 메일이 없을 때도 "확인 완료"로 알린다.
